T1跟随系统，不自己记。mac 是「外观」设置，Windows 是「个性化 → 颜色」。工具跟着走，不给第二个开关——多一个开关就多一处不一致。

T3语义色要分别调。明亮下的深红 #C70013 放到深底上会糊成一团，暗色必须换成系统红 #FF453A。四个状态色都是各调一次，不是取反。
T4暗色的浮窗靠描边立住。深色背景上投影几乎不可见，所以暗色主题把阴影换成 0.5px 的半透明白描边 + 更深的投影。这是两套主题里差别最大的地方。
T5菜单栏图标在两种主题下是同一个模板图标——mac 会自动反色。所以正常态在亮菜单栏上是深色、在暗菜单栏上是浅色，我们不用管。

M1图标取最严重的一个：卡住 > 可疑 > 正常。角标写「2」表示有两个目标在报警。这样一眼就够，不用点开数。

M3每个目标一行，第二行小字是该目标当前的出口——节点名或本地端口。看到「日本专线04」就知道这条走哪个节点，不用展开。

M6「Claude Code 本体」是个有用的天然对照：直连不走代理，如果它正常而 ReClaude 卡住，基本就能确定是代理或中继的问题，不是官方 API 的问题。

发现：从正在跑的流量里挑要盯的

新增

不让你手写配置。工具直接从 mihomo 读出此刻所有正在跑的连接，连同它走哪个节点，列出来让你勾。 实测能拿到主机名和节点名——但拿不到进程归属（find-process-mode: strict 开着也全是空，mihomo 在 macOS 上拿不到对端进程），所以按域名挑，不按进程挑。这反而更稳：通配符能盖住以后新增的子域。

F1列表就是这个工具的数据源本身。它读的 mihomo 接口，和判定时读的是同一个——所以「能看见的」必然「能盯上」，不会出现列出来了却监控不了。
F2按域名不按进程。实测进程归属拿不到（20 条连接 process 字段全空），所以不假装能按进程过滤。域名这一层已经足够——你要盯的就是那几个 AI 域名。
F3选一个域名会建议通配符。如上图点 misaka.route.reclaude.ai，底部提示加入 *.reclaude.ai——这样以后 dl.reclaude.ai 之类的新子域自动被盯上，不用回来改配置。
F4已盯的标出来。relay 和 misaka 两行带「已盯」标签，颜色是强调蓝——你就知道这两个已经在看，不会再重复加。
F5每行直接显示当前节点。列表里就能读到 🇯🇵日本高速03——你现在手切 Clash，一眼就能确认切完有没有生效，不用回 Clash 界面看。
F6纯观测，不带任何动作。不切节点、不改路由、不碰你的 Clash 配置——按你说的，切节点你自己来，工具只负责让你看见。
04

加监控目标 = 改配置，不改代码

新增

你说以后想加新类别。所以「目标」不是写死的，是一份配置。判断逻辑本身是通用的——它只认两件事：有没有进展、有没有报错。 任何能提供这两件事的数据源都能接进来，加新目标只写一个配置文件里的一节。

~/.stall-watch/targets.yaml 
# 加一个目标：复制一节，改名字和数据源。不用重新编译。
defaults:
  suspect: 10s        # 超过这个没进展 → 可疑
  stall: 30s          # 超过这个还没进展 → 卡住
  local_busy_mute: true  # 本地工具在跑时不判定

targets:

  # ── 已有的两个 ──────────────────────────────
  - name: reclaude
    label: ReClaude
    sources:
      - type: mihomo
        hosts: ["*.reclaude.ai"]
      - type: logtail
        path: ~/.reclaude/logs/daemon.log
        error: ' (429|50[0-9]) '

  - name: mirasim
    label: Mirasim Cloud
    sources:
      - type: mihomo
        hosts: ["*.mirasim.ai"]
      - type: logtail
        path: ~/Library/Caches/reclaude-mirasim/launch.log
        progress: 'event=turn-(first-output|result)'

  # ── 以后加新的，就这样加 ─────────────────────
  - name: 内部对账服务
    label: 对账服务
    sources:
      - type: endpoint
        port: 8091
        process: recon-svc
      - type: logtail
        path: ~/logs/recon.log
        progress: 'processed=\d+'
        error: 'ERROR|timeout'
    suspect: 20s
    stall: 90s       # 对账慢，阈值放宽
X1五种内置数据源，覆盖绝大多数情况：mihomo（代理连接字节）、logtail（任意日志）、endpoint（本地端口/进程）、hook（Claude Code 事件）、frame（stream-json 帧日志）。新目标基本都能拼出来。
X2判断逻辑跟目标解耦。引擎只问数据源两个问题：「有进展吗」「有报错吗」。它不知道 reclaude 是什么，也不知道对账服务是什么。所以加目标不需要碰判定代码——这是扩展性的全部秘密。
X3阈值可按目标覆盖。对账服务天生慢，stall: 90s；AI 请求 30s 就该报。写死在代码里就废了。
X4什么时候才需要改代码：出现一种新形态的数据源（比如 Kafka 消费延迟、K8s 探针）。那时候加一个 adapter，接进同一套注册表，判定逻辑仍然不动。这是有意留的接口，不是事后补的。
X5界面上「添加目标…」走一个表单，填完写进同一个 yaml——手改配置和界面添加是同一份数据，不会两边不同步。
X6Windows 上路径换成 %USERPROFILE%\.stall-watch\targets.yaml，其余一模一样。
05

数据源、判定规则

这张表决定上面所有 UI 显示什么。放在草图阶段就是让你能先挑判据的错——判据错了 UI 再好看也没用。

数据源读什么在 reclaude / mirasim 上怎么用
mihomo代理连接上行/下行字节数*.reclaude.ai 和 *.mirasim.ai，字节不增才算停
logtail任意日志文件的匹配行reclaude daemon.log 抓 429/50x；mirasim launch.log 抓回合事件
endpoint本地端口是否响应、进程是否在判断本地代理是否活着（如端口 7890）
hookClaude Code 的 PreToolUse / PostToolUse判断「该不该静默」——跑本地工具时不判定
framestream-json 帧日志mirasim 启动器已有回合首包/结果毫秒数
形态现象判据面板显示给什么动作
A 线路停字节流中途冻结连接字节连续 30s+ 无增量，且日志无错误A 线路停切到其他节点
B 上游卡服务慢 / 报错字节在动，但日志出现 429 / 502 / 503 / 504B 上游 503切 gateway 线路
C 账号配额风控换号、5 小时窗口日志出现换号或配额线索C 账号配额等待 / 查订阅
D 本地忙Claude 在跑本地命令hook 报告正在跑工具D 不判定无（不报警）
思考中真的在想事情字节在动、日志干净、只是还没出新帧思考中 · n 秒无（阈值放宽）

实测依据：空闲连接的字节增量常态就是 0（30 秒采样里，11 条连接有 8 条每秒增量全为 0）。所以光盯字节必然误报——「该不该有数据」不是补充信号，是主干。

W1Windows 多一个「暂停监控」，mac 没有。Windows 上跑长任务更常见，需要一个明确的「别烦我」；mac 靠自动不判定，但给个手动开关更稳。

要你定
先做哪些目标？
我推荐先只做 ReClaude 和 Mirasim 两个，其余的先在配置里留空。理由是 Phase 0 要验的是判据对不对，目标越多噪声越多、越难看出是判据错还是目标设错。加目标很容易，但一开始全上会让你分不清哪个在误报。
要你定
「切节点」按钮 Phase 0 要不要就接上？
我倾向Phase 0 不接，按钮先只放「复制诊断」。卡顿分四种，只有 A 类切了有用；判据没验准之前就切，可能把 B 类越切越糟。但这会让 Phase 0 看起来「没什么用」——你要想早点有手感也可以先接上。
要你定
这工具叫什么名字？
我暂用「卡顿哨兵」。定个名字才好定图标、包名、菜单文案。
